# W Tap gameplay test — 2026-10-30

Tested on a local vanilla Minecraft Java 26.3 server with two Fabric clients. PlayerA attacked PlayerB with an iron sword while physically holding W. Both began at `(5.5, 100, 5.5)` and `(7.8, 100, 5.5)` respectively for each run. PlayerA was sprinting before each attack. Only W Tap was enabled in the enhanced run; all other combat modules were disabled. The test used an 8-tick release so the server could sample the pause. The shipped default is 2 ticks and was not independently measured.

The 26.3 client source shows `Minecraft.tick` handles attack input before ticking the player, and `KeyboardInput.tick` reads the forward key state during the player tick. W Tap suppresses that key state after the attack, sends a sprint-stop command, and later uses `KeyMapping.setAll()` to restore the physically held key. It sends sprint-start only if W is still held. The server sprint state was sampled with its inline entity-flags predicate.

| Run | Sprint before | Sprint at mid-test sample | Sprint after release | PlayerA X at mid-test sample | PlayerB health |
| --- | --- | --- | --- | ---: | ---: |
| W Tap on | true | false | true | 6.8883 | 14 |
| W Tap off | true | false | false | 7.8243 | 14 |

The matched mid-test sample showed about 0.94 blocks less forward movement with W Tap. The control stopped sprinting after the hit and did not restart it. In a separate W Tap run, releasing W immediately after the attack left the server sprint state false after the tap, confirming that the module did not force sprint when forward input had ended.

The positional samples are sensitive to server tick timing, so they establish the direction and approximate size of the pause in this setup rather than an exact per-tick speed. Compatibility with third-party anticheats has not been tested.
